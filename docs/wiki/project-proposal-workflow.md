# 🌱 **ROOTS — Workflow de Propostas de Projeto**


Este documento descreve o processo completo para propor, discutir, validar e iniciar um novo projeto no ROOTS. O objetivo é garantir transparência, organização e uma boa experiência para todos os membros.


## Resumo do Workflow

O típico ciclo de vida de um projeto é o seguinte:

```
Ideia 
   ↓
Proposta
   ↓
Discussão
   ↓
Validação
   ↓
Aprovação
   ↓
Criação do Repositório
   ↓
Kickoff
   ↓
Desenvolvimento (e atualizações à comunidade)
   ↓
Arquivo / Encerramento
```


## 💡 **1. Validar a ideia**

Antes de abrir uma proposta formal:

1. Verifica se já existe um projeto semelhante.
2. Partilha uma mensagem breve em **Discussions > Comunidade: Conversa Geral** para sentir o interesse.
3. Tenta identificar possíveis colaboradores ou mentores.

> ℹ️ Esta fase é informal e serve apenas para evitar duplicações e alinhar expectativas.

---

## 📝 **2. Criar a Proposta**

O proponente deve:

1. Ir a **Discussions > 💡 Ideias de Projetos ou Eventos**.
2. Criar um novo tópico com o título:
   **`[PROJETO] Nome da proposta de projeto`**
3. Copiar e preencher o template disponível [aqui](./project-proposal-template.md).

A proposta deve descrever:

* Objetivo do projeto
* Motivação
* Resultados esperados
* Mockups (opcional)
* Tecnologias sugeridas
* Público-alvo
* Equipa inicial (se houver)
* Nome proposto do repositório

---

## 💬 **3. Discussão Aberta**

Assim que a proposta é publicada:

* Toda a comunidade ROOTS pode comentar.
* Pode-se sugerir melhorias, alternativas tecnológicas, etc.
* Interessados podem manifestar vontade de participar.

Regras desta fase:

* Discussões devem seguir o **Código de Conduta**.
* O proponente continua a atualizar o tópico com revisões, se necessário.
* A discussão deve estar ativa por um **mínimo de 7 dias** para recolher *feedback*.

---

## ✔️ **4. Validação Inicial**

Para avançar, é necessário:

1. **Pelo menos 2 membros interessados** (incluindo o proponente).
2. **Viabilidade técnica ou conceptual** considerada razoável pela comunidade.
3. **Sinal verde do Núcleo de Organização/Coordenador Geral** (adicionalmente, de um mentor quando for hardware/eletrónica).

Esta validação não significa “aprovação formal”, apenas confirma que:

* ✅ Há equipa suficiente;
* ✅ Ideia tem propósito claro;
* ✅ É adequada ao ROOTS.

---

## 🗳️ **5. Aprovação**

A aprovação é simples e segue um dos seguintes caminhos:

> [!WARNING]
> O Coordenador Geral tem poder de "veto", se o projeto potencialmente violar algum dos princípios do ROOTS. 

### **A. Aprovação por consenso (“lazy consensus”)**

Se após a fase de discussão:

* não houver objecções fundamentadas
* houver apoio de vários membros
* equipa mínima estiver formada

➡️ A proposta é **aprovada automaticamente**.

### **B. Aprovação formal (se necessário)**

Se houver desacordo, ambiguidades ou dúvidas:

* Núcleo de Organização decide por maioria simples.
  * Pode consultar mentores (especialmente em projetos de hardware).

---

## 📂 **6. Criação do Repositório**

Após aprovação:

1. Um responsável do Núcleo de Organização do ROOTS cria o repositório na organização, com o nome acordado.
   - ℹ️ Por uma questão de uniformização e identidade, todos os nomes de repositórios terão o formato `roots-<nome projeto>`
  
2. O repositório é inicializado com:

   * Documentos *template* (a editar pelo grupo do projeto):
      - `README.md`
      - `CHANGELOG.md`
      - `CONTRIBUTING.md`
   * `LICENSE` - Licença open-source Apache 2.0
   * Estrutura base (se aplicável)

3. É criada uma *Team* (equipa GitHub, para facilitar a gestão de permissões) para esse projeto, contendo os membros iniciais.
   - ℹ️ Para facilitar a identificação das equipas dos projetos, os nomes das equipas seguirão a nomenclatura `team-<nome projeto>`.

4. A equipa do projeto recebe permissões adequadas para o repositório respetivo.

---

## 🚀 **7. Kickoff do Projeto**

O proponente (agora líder inicial do projeto) organiza:

* Reunião curta (presencial ou online) para alinhamento inicial, cujo *output* deverá ser:
  * Um *Roadmap* para o desenvolvimento;
  * Primeiras *tarefas* para dividir trabalho.

* A equipa atualiza o `README` do projeto, incluindo o *roadmap* decidido.

---

## 🔄 **8. Desenvolvimento**

Durante o desenvolvimento:

* O projeto deve manter um **changelog**.
* Contribuições seguem o guia de *Contributing*.
* Estado do projeto deve ser atualizado no tópico respetivo de **Discussions** com informação à comunidade de avanços relevantes efetuados. 
* Deverão ser efetuadas *releases*, se aplicável.

---

## 🧹 **9. Arquivar / Encerrar um Projeto**

É possível arquivar um projeto se:

* estiver completo;
* não tiver atividade por > 1 ano, ou;
* a equipa solicitar encerramento.

O arquivamento é decidido por:

* A equipa do projeto **+** O Núcleo de Organização.

**O repositório permanece visível para consulta.**
